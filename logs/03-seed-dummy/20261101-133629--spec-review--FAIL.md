# Spec review — 03-seed-dummy

- Date: 20261101-133629
- Feature: 03-seed-dummy
- Phase: 1 (Spec)
- Verdict: **FAIL** (spec validation by the author, 2026-11-01)

## Verdict

The extraction is faithful and the design is sound, but three blocking items would either fail an acceptance criterion as written or break the integration suite.

## Blocking

1. **B1 Tests would wipe the shared test database.** AC-1 to AC-5 ran `seed-dummy` against the local test Postgres that every other integration test uses, in parallel; its `TRUNCATE` would delete their fixtures mid-run.
2. **B2 `FROM_CLIENT_ID` on staging.** The sender id came from the operator's environment (default `1`), while the staging app reads Vercel Preview's value; if they differ, docket creation on staging fails (and AC-10 with it).
3. **B3 "Every list has more than one page" is impossible.** Users aren't seeded, categories are limited to v1's names, dockets had a minimum of 20, and product types, sizes and media had no minimum.

## Non-blocking

1. **N1** `TRUNCATE` and foreign keys: the split between restarted and kept sequences needs one `TRUNCATE … CONTINUE IDENTITY` plus `ALTER SEQUENCE … RESTART`.
2. **N2** Category flags: use v1's real `show_*` flags from a shared committed constant, and say where the v1 list comes from.
3. **N3** AC-5 needs a test seam to force a failed insert.
4. **N4** AC-6/AC-7 don't say how "without opening a database connection" is proven.
5. **N5** `--target local` doesn't check the host, so a leftover Neon URL in the shell could be wiped.
6. **N6** `orders.date` and `delivery_dockets.date` default to `current_date`, which breaks AC-2 across days.
7. **N7** The `seed:dummy` npm script isn't listed.

## Questions for the author

1. OQ-2: confirmation prompt for `--target staging`?
2. B2: require `FROM_CLIENT_ID` for staging, or pin a fixed sender id?
3. B3: narrow the paging claim, or raise every minimum above 25?
