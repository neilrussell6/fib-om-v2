## Summary

The change does what the spec says. All 27 acceptance criteria are met; no high or critical
issues. Every Server Action checks the session first, all SQL values are parameters (the only

## Findings

1. **Severity: medium** — `lib/order-items/panel-actions.ts:97`. A stale panel can undo another
   user's change to the order. The panel always sends the order's due date and status as loaded;
   the server writes them whenever they differ from the stored values. Scenario: A opens item X
   (order due 10 Nov); B changes the order's due date to 20 Nov; A changes only Quantity and
   saves; the order (every item on it) silently goes back to 10 Nov. Same for status. The code
   follows the spec's rule; the spec didn't consider staleness.
   *Accepted fix (not applied):* send `order_due_date`/`order_status` only when dirty (picking a
   new Order marks them dirty); make them optional on the server and leave the order alone when
   absent; integration test for the stale case.
2. **Severity: low** — `components/order-items/order-item-panel.tsx:143`. Opening the panel
   pushes a history entry, closing replaces it, so history ends up "list → list" and the first
   Back after closing seems to do nothing. AC-24 still holds.
   *Accepted fix (not applied):* mark list-opened panels (row click, View action) and close them
   with `router.back()`; keep `replace` for directly loaded `?item=` URLs; e2e test.
3. **Severity: low** — `components/order-items/order-item-panel.tsx:54`. Below 1024px the server
   renders the desktop side panel, then swaps to the sheet after hydration, so the list is briefly
   squeezed beside a ≥320px panel on direct loads.
   *Accepted fix (not applied):* `max-lg:hidden` on the desktop `<section>`; an e2e check with
   JavaScript disabled at 800px.
